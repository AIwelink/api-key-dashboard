# 阶段四：数据理解、分层事件窗口与长期记忆设计

本文档承接：

```text
docs/agent/账号池运营Agent总体架构.md
docs/agent/阶段一-Agent-LLM配置与调用层设计.md
docs/agent/阶段二-Agent持久化与前端缓存任务.md
docs/agent/阶段三-Context-Pack与LLM主决策设计.md
```

阶段一已经完成 Agent LLM 配置与 LangChain 调用层。
阶段二已经完成 Agent run、message、decision 的持久化，以及前端刷新后的状态恢复。
阶段三已经完成 Context Pack 与 LLM 主决策，让补号数、风险等级、告警建议等业务判断优先由 LLM 输出，后端只做结构校验和安全保护。

阶段四暂不进入定时 loop，也暂不接入钉钉告警自动启动。

本阶段重点解决三个问题：

1. 让 LLM 更好地理解账号池运营数据，而不是只看到一堆零散指标。
2. 把事件流按窗口分层：最近 24h 明细最多 80 条，最近 1h / 6h / 24h / 7d 做聚合摘要。
3. 建立高级长期记忆，让 Agent 自己沉淀经验，而不是每次都把 7d 全量事件塞进上下文。

## 1. 阶段目标

阶段四的目标不是增加更多动作，而是提高 Agent 的“观察质量”和“经验积累能力”。

完成后，Agent 每次运行时应能看到：

- 当前账号池的关键运营事实。
- 容量指标的业务含义。
- 事件流在不同时间窗口中的变化。
- 最近 24h 内关键事件明细。
- 最近 1h / 6h / 24h / 7d 的事件聚合摘要。
- 历史 Agent 决策和长期记忆摘要。
- 数据不足、数据过期、事件缺口等上下文质量提示。

LLM 不应该只看到：

```text
five_hour_peak_multiple = 0.56
burst_1h_multiple = 3.25
detected_401_24h = 18
```

而应该同时看到这些指标被整理后的运营解释：

```text
最近一天 5h 峰值容量倍数为 0.56x，表示当前使用池容量只能覆盖最近峰值需求的 56%，峰值需求已经超过当前池子可承载能力。
突发 1h 预估为 3.25x，表示按当前小时速度折算到 5h 后，当前容量可以覆盖约 3.25 倍需求，短时突发压力暂时可承载。
最近 24h 出现 18 个 401，且事件流显示集中发生在中午同一时间段，更像一次批量封号或同批账号异常，而不是全天持续随机掉号。
```

阶段四的核心交付是 Context Pack v2，而不是新的执行动作。

## 2. 不做范围

阶段四暂不做：

- Agent 自动定时 loop。
- 钉钉告警自动发送。
- 告警事件自动触发 Agent。
- 自动补号、推号、买号、删号。
- 自动修改账号池配置。
- 人工确认后的动作执行。
- 多账号池批量巡检。
- LangGraph 状态机重构。

这些能力仍然放到后续阶段。

阶段四只做只读观察、上下文增强、长期记忆沉淀和 LLM 理解能力提升。

## 3. 当前问题

阶段三后，Agent 已经能把 Context Pack 给 LLM，并让 LLM 输出主决策。

但当前仍有明显问题：

- LLM 容易把规则引擎或历史字段当成主要判断依据。
- LLM 不一定理解 `0.56x`、`3.25x`、动态 5h 容量、7d 容量、预估天数等指标的业务含义。
- 事件流没有被充分利用，模型不知道 401 是否集中在同一时间段。
- 模型可能在上下文已有事件证据时，仍然追问“是否集中发生”。
- 最近事件、短期趋势、长期模式没有分层。
- 长期记忆目前主要是最近消息和最近决策，不是运营经验。
- 如果直接塞 7d 全量事件，会导致上下文过大、噪声过多、模型抓不住重点。

所以阶段四要把“数据”进一步变成“可被模型理解的运营事实”。

## 4. 阶段四总体流程

阶段四后的手动触发流程仍然是：

```text
点击分析 / 用户自然语言提问
  |
  v
创建 agent_run
  |
  v
构建 Context Pack v2
  |
  v
生成 Operational Facts
  |
  v
读取分层事件窗口
  |
  v
读取长期记忆摘要
  |
  v
调用 LLM 主决策
  |
  v
校验、保存 decision、保存 assistant message、完成 run
```

其中新增的重点是：

```text
raw metrics
  -> capacity dictionary
  -> operational facts
  -> event windows
  -> memory summaries
  -> LLM decision
```

也就是说，阶段四不改变“LLM 是主决策者”的原则，但要显著提高 LLM 拿到的上下文质量。

## 5. Context Pack v2 结构

阶段四建议把 Context Pack 升级为：

```json
{
  "schema_version": "agent_context_pack.v2",
  "run": {},
  "target_pool": {},
  "capacity": {},
  "capacity_dictionary": {},
  "operational_facts": {},
  "event_windows": {},
  "probe": {},
  "recent_agent_decisions": [],
  "recent_conversation": [],
  "long_term_memory": {},
  "system_constraints": {},
  "data_quality": {}
}
```

### 5.1 capacity

`capacity` 保存从主系统读取到的原始或半结构化容量数据。

示例：

```json
{
  "account_type": "pro",
  "single_account_5h_limit_usd": 360,
  "single_account_7d_limit_usd": 2100,
  "active_account_count": 6,
  "reserve_account_count": 0,
  "dynamic_5h_total_usd": 2160,
  "dynamic_5h_used_usd": 776,
  "dynamic_5h_available_usd": 1384,
  "actual_5h_available_usd": 846,
  "dynamic_7d_total_usd": 12600,
  "dynamic_7d_used_usd": 1470,
  "dynamic_7d_available_usd": 11130,
  "recent_day_5h_peak_multiple": 0.56,
  "seven_day_highest_5h_peak_multiple": 0.25,
  "burst_1h_estimated_5h_multiple": 3.25,
  "burst_trend_label": "rising",
  "burst_trend_strength": "medium",
  "recent_24h_runway_days": 1.4,
  "seven_day_highest_24h_runway_hours": 21.6,
  "recent_24h_estimated_account_consumption": 3.8,
  "seven_day_highest_24h_estimated_account_consumption": 5.9
}
```

注意：这里保存的是数据，不负责最终判断“补多少号”。

### 5.2 capacity_dictionary

`capacity_dictionary` 用来告诉 LLM 这些指标是什么意思。

这部分是稳定解释，不是当前池子的判断结果。

示例：

```json
{
  "single_account_5h_limit_usd": "单个 pro 账号在 5h 窗口内可用额度，当前按 360 美元理解。",
  "single_account_7d_limit_usd": "单个 pro 账号在 7d 窗口内可用额度，当前按 2100 美元理解。",
  "dynamic_5h_total_usd": "综合账号当前已用比例和未来刷新恢复额度后，估算出的 5h 动态总容量。",
  "dynamic_7d_total_usd": "综合账号当前 7d 已用比例和未来刷新恢复额度后，估算出的 7d 动态总容量。",
  "recent_day_5h_peak_multiple": "最近一天最高 5h 峰值需求与当前 5h 容量的覆盖关系。小于 1 表示当前容量低于峰值需求，大于 1 表示当前容量可以覆盖峰值需求。",
  "burst_1h_estimated_5h_multiple": "把当前小时已用按当前小时进度折算成完整 1h，再折算成 5h 压力后，与当前 5h 容量的覆盖关系。",
  "recent_24h_runway_days": "按最近 24h 消耗速度估算当前 7d 可用容量还能支撑多久。",
  "estimated_account_consumption": "按 24h 消耗金额除以单账号 7d 限额折算出的账号消耗速度。"
}
```

这一步的意义是降低 LLM 对指标名称的误解。

### 5.3 operational_facts

`operational_facts` 是阶段四的关键新增层。

它不替 LLM 做最终决策，也不计算补号数，而是把原始数据翻译成可读的运营事实。

建议结构：

```json
{
  "capacity_facts": [],
  "usage_facts": [],
  "burst_facts": [],
  "event_facts": [],
  "probe_facts": [],
  "memory_facts": [],
  "data_quality_facts": [],
  "risk_signals": [],
  "data_gaps": []
}
```

示例：

```json
{
  "capacity_facts": [
    "当前 pro 池实际使用池 5h 动态总容量约为 2160 美元，备用池容量为 0。",
    "最近一天 5h 峰值容量倍数为 0.56x，表示当前池子只能覆盖最近峰值需求的约 56%，近期峰值已经超过当前容量。",
    "7d 总容量约为 12600 美元，当前 7d 可用额度约为 11130 美元，长期额度剩余比例较高。"
  ],
  "usage_facts": [
    "按最近 24h 消耗 8038 美元估算，当前容量约可支撑 1.4 天。",
    "按 7d 最高 24h 消耗 12398 美元估算，极端压力下可支撑约 21.6 小时。"
  ],
  "burst_facts": [
    "突发 1h 预估容量倍数为 3.25x，说明按当前小时速度折算，短时突发暂时可承载。",
    "最近 1h 趋势为上涨，中等强度，近 3h 均值比前 3h 高 26%。"
  ],
  "event_facts": [
    "最近 24h 出现一批账号状态异常，主要集中在中午时间段。",
    "401 事件不是均匀分布，存在集中爆发特征。"
  ],
  "risk_signals": [
    {
      "signal": "recent_peak_capacity_gap",
      "level": "high",
      "evidence": "recent_day_5h_peak_multiple=0.56"
    },
    {
      "signal": "no_reserve_pool",
      "level": "medium",
      "evidence": "reserve_account_count=0"
    }
  ]
}
```

`operational_facts` 可以由后端确定性生成，因为它只做解释和归纳，不做最终业务决策。

最终是否补号、补多少号、是否告警、是否人工确认，仍然由 LLM 基于这些事实判断。

## 6. 分层事件窗口

主系统已有事件记录页面，事件流包含账号状态变化、封号、限额、错误变化等信息。

阶段四要让 Agent 正确使用事件流。

### 6.1 事件窗口设计

事件数据分成两类：

```text
明细事件：最近 24h，最多 80 条
聚合摘要：最近 1h / 6h / 24h / 7d
```

不要每次把 7d 全量事件塞给 LLM。

原因：

- 7d 全量事件太长，容易淹没重点。
- LLM 更需要知道趋势、集中爆发、事件类型分布，而不是读完每一条旧事件。
- 长期模式应该进入长期记忆，而不是每轮都靠全量上下文重新推理。

### 6.2 event_windows 结构

建议结构：

```json
{
  "detail_24h": {
    "window_hours": 24,
    "max_items": 80,
    "items": []
  },
  "summary_1h": {},
  "summary_6h": {},
  "summary_24h": {},
  "summary_7d": {},
  "notable_patterns": [],
  "data_quality": {}
}
```

### 6.3 detail_24h

最近 24h 明细用于让 LLM 看见“具体发生了什么”。

最多 80 条，优先保留高价值事件：

- 账号封禁。
- 401 / authentication_error。
- 账号恢复。
- 5h limit reached。
- 7d limit reached。
- 状态从 active 变为 disabled / banned / limited。
- 错误类别变化。
- 同一账号短时间连续异常。
- 同一时间段批量异常。

建议每条事件保留字段：

```json
{
  "event_id": "...",
  "occurred_at": "2026-07-01T12:10:00+08:00",
  "site_id": "...",
  "pool_id": "...",
  "group_id": 5,
  "account_id": "...",
  "account_email_masked": "abc***@example.com",
  "event_type": "account_status_changed",
  "severity": "warning",
  "from_status": "active",
  "to_status": "banned",
  "error_category": "authentication_error",
  "message": "401 Invalid authentication credentials"
}
```

敏感字段需要沿用主系统已有脱敏策略。

### 6.4 summary_1h

最近 1h 摘要用于判断即时突发。

建议包含：

```json
{
  "window": "1h",
  "total_events": 12,
  "account_count": 8,
  "event_type_counts": {},
  "status_transition_counts": {},
  "error_category_counts": {},
  "first_event_at": "...",
  "last_event_at": "...",
  "clusters": [],
  "top_accounts": [],
  "interpretation": []
}
```

重点回答：

- 最近 1h 是否突然封号。
- 401 是否集中爆发。
- 是否出现大批量限额。
- 是否和突发消耗趋势同向。

### 6.5 summary_6h

最近 6h 摘要用于判断短期运营态势。

重点回答：

- 今天是否出现明显拐点。
- 最近几小时是否持续恶化。
- 异常是单点爆发后停止，还是持续发生。
- 是否和峰值、突发趋势对应。

### 6.6 summary_24h

最近 24h 摘要用于判断当天运营状态。

重点回答：

- 今天掉了多少号。
- 今天恢复了多少号。
- 今天 401 / 限额 / 错误变化分别是什么量级。
- 是否存在集中时间段。
- 是否存在某个池、某个站点、某类账号集中异常。

### 6.7 summary_7d

最近 7d 摘要用于判断长期质量和周期。

只给聚合摘要，不给全量明细。

重点回答：

- 过去 7d 哪天掉号最多。
- 最近 7d 是否存在固定时段爆发。
- 是否存在某个账号来源、账号池或站点质量下降。
- 最近几轮补号后存活表现如何。
- 当前异常是否高于过去 7d 常态。

### 6.8 事件聚类

事件摘要应尽量识别聚类。

聚类维度包括：

- 时间聚类：例如 10 分钟内出现大量 401。
- 账号聚类：同一批账号连续异常。
- 池聚类：同一个 pool_id 集中异常。
- 站点聚类：同一个 site_id 集中异常。
- 错误聚类：同一种 error_category 集中出现。

建议输出：

```json
{
  "clusters": [
    {
      "cluster_type": "time_burst",
      "window_start": "2026-07-01T12:00:00+08:00",
      "window_end": "2026-07-01T12:20:00+08:00",
      "event_count": 18,
      "account_count": 18,
      "dominant_event_type": "authentication_error",
      "dominant_error_category": "401",
      "interpretation": "401 集中发生在中午同一时间段，更像批量封号或同批账号失效。"
    }
  ]
}
```

这样 LLM 就不应该再追问“是否集中发生”，因为上下文已经给出答案。

## 7. 长期记忆设计

阶段二的记忆主要是：

- 最近 run。
- 最近 decision。
- 最近 conversation messages。

这些是运行记录，不等同于长期运营经验。

阶段四要新增长期记忆层，但仍然只写 Agent 自己的集合，不写账号池业务表。

### 7.1 长期记忆目标

长期记忆用于让 Agent 逐渐知道：

- 某个池过去常见风险是什么。
- 哪些时段容易出现封号。
- 哪些事件组合通常意味着需要快速补号。
- 上一次建议是否有效。
- 补号后容量是否恢复。
- 哪些判断曾经被人工纠正。
- 某个池最近的基线消耗速度是多少。
- 某个池常态 401 水平是多少。
- 最近一周账号存活质量是否变差。

长期记忆不是把所有历史事件原样存下来，而是保存 Agent 总结后的经验。

### 7.2 建议新增集合：agent_memory_summaries

```json
{
  "_id": "...",
  "memory_id": "...",
  "site_id": "...",
  "pool_id": "...",
  "memory_type": "pool_daily_summary | pool_weekly_summary | decision_review | operator_feedback_summary | survival_pattern",
  "period_start": "2026-07-01T00:00:00+08:00",
  "period_end": "2026-07-01T23:59:59+08:00",
  "summary": "...",
  "facts": [],
  "patterns": [],
  "lessons": [],
  "risk_baselines": {},
  "created_by": "agent",
  "created_at": "...",
  "source_run_ids": [],
  "source_decision_ids": []
}
```

### 7.3 memory_type

建议先支持以下类型：

```text
pool_daily_summary
pool_weekly_summary
decision_review
operator_feedback_summary
survival_pattern
```

#### pool_daily_summary

每天对某个池生成一条运营摘要。

内容包括：

- 当天容量变化。
- 当天消耗速度。
- 当天掉号和恢复。
- 当天最大风险时段。
- 当天 Agent 建议。
- 当天人工反馈。

#### pool_weekly_summary

每周对某个池生成一条质量摘要。

内容包括：

- 一周内账号存活质量。
- 典型异常时间段。
- 高风险事件组合。
- 一周内补号建议是否偏保守或偏激进。

#### decision_review

对历史决策做复盘。

内容包括：

- 当时 Agent 建议补多少号。
- 后续容量是否改善。
- 后续是否继续封号。
- 人工是否采纳或纠正。
- 该决策是否值得以后参考。

#### operator_feedback_summary

总结人工反馈。

例如：

- “负责人认为夜间超并发时应更积极告警。”
- “某类账号近期质量差，建议降低信任度。”
- “某个池白天优先人工确认。”

#### survival_pattern

总结账号存活规律。

例如：

- “过去 7d 新增 pro 账号中，中位存活时间下降。”
- “某批账号经常在导入后 24h 内出现 401。”

## 8. 长期记忆写入时机

阶段四先设计三种写入时机。

### 8.1 每次 Agent run 后轻量总结

每次 Agent 成功完成后，可以保存一条轻量记忆候选。

但不建议每次都写入长期记忆正式摘要，否则会产生大量重复内容。

可先写入 run 内：

```json
{
  "memory_candidates": [
    "今天中午出现一次 401 集中爆发。",
    "当前池子备用账号为 0，是本次判断的重要风险。"
  ]
}
```

当前实现落点：

- `backend/app/modules/agent/long_term_memory.py` 提供 `build_memory_candidates_from_report(...)`。
- `backend/app/modules/agent/orchestrator.py` 在每次成功生成 report 后，把候选写入 `report["agent"]["memory_candidates"]`。
- `finish_agent_run(...)` 会把 `agent` 字段保存到 `agent_runs`，因此轻量候选随 run 留存。
- 这一步不写入 `agent_memory_summaries`，避免每次运行都制造重复长期记忆。

### 8.2 每日汇总

每日汇总是长期记忆的主要入口。

后续接 loop 后可定时生成。

当前阶段可以先提供服务函数，不一定立即自动调度。

```text
generate_daily_memory_summary(pool_id, date)
```

当前实现落点：

- `backend/app/modules/agent/long_term_memory.py` 提供 `generate_daily_memory_summary(...)`。
- 函数会读取当天的 `agent_runs`、`agent_decisions`、`agent_messages` 和当前事件窗口摘要。

## 9. Context Pack 中如何使用长期记忆

每次 Agent 决策时，不加载所有长期记忆。

只加载和当前池相关的少量摘要：

```text
最近 3 条 daily summary
最近 2 条 weekly summary
最近 3 条 decision review
最近 5 条人工反馈摘要
```

建议 Context Pack 中结构：

```json
{
  "long_term_memory": {
    "pool_daily_summaries": [],
    "pool_weekly_summaries": [],
    "decision_reviews": [],
    "operator_feedback_summaries": [],
    "survival_patterns": []
  }
}
```

这能让 Agent “记住经验”，但不会把历史噪声全部塞进 LLM。

当前实现落点：

- `backend/app/modules/agent/context_pack.py` 在构建 Context Pack v2 时调用 `get_agent_long_term_memory(...)`。
- `backend/app/modules/agent/long_term_memory.py` 中默认加载范围为：
  - `daily_limit=3`
  - `weekly_limit=2`
  - `decision_review_limit=3`
  - `feedback_limit=5`
  - `survival_pattern_limit=3`
- 查询优先按当前 `pool_id` 过滤；如果没有 `pool_id`，才按 `site_id` 降级读取站点级记忆。

- 本轮用户消息如果被识别为人工反馈，会在本次 Context Pack 构建之后写入长期记忆，因此主要影响后续决策，不强行影响当前这一次判断。

- 不执行补号、推号、买号、删号。
- 不自动发送钉钉。
- 仍然只保存 Agent 自己的 run、message、decision、memory。

### 15.5 构建验收

```text
python -m compileall backend\app
npm run build
```

## 16. 开发顺序建议

建议按以下顺序开发：

1. 扩展 `event_stream.py`，实现 1h / 6h / 24h / 7d 聚合摘要和 24h 明细限制。
2. 新增 `operational_facts.py`，生成容量字典和运营事实。
3. 新增 `long_term_memory.py`，实现长期记忆保存和读取。
4. 给 `agent_memory_summaries` 增加 bootstrap 索引。
5. 修改 `context_pack.py`，升级到 `agent_context_pack.v2`。
6. 修改 `decision_core.py` prompt，让 LLM 优先使用 operational facts、event windows、long term memory。
7. 修改 `memory.py` 或 orchestrator 保存 context pack 摘要中的新字段。
8. 视情况微调前端展示，只展示事件判断摘要，不展示完整事件明细。
9. 运行后端编译和前端构建。
10. 用真实 pro 池数据进行人工验收，重点看 LLM 是否能识别事件集中爆发和容量指标含义。

## 17. 与后续阶段的关系

阶段四完成后，Agent 的观察能力会明显增强。

后续再进入自动 loop 时，Agent 才有足够稳定的上下文基础：

```text
阶段四：看懂数据，分层事件，沉淀记忆
阶段五：定时自启动 loop
阶段六：告警事件触发和钉钉通知
阶段七：人工确认后的动作流
```

如果跳过阶段四直接做 loop，Agent 只会定时重复调用一个“不太会看数据”的 LLM。
所以阶段四是让 Agent 从“能回答”走向“能观察、能理解、能积累经验”的关键阶段。
