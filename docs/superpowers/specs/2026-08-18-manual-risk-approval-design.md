# AIWeLink 人工封禁审批与运营权限设计

**日期：** 2026-08-18
**状态：** 已确认，待书面复核
**目标分支：** `achernar/dev`

## 1. 背景

AIWeLink 风控当前支持自动封禁。线上在 2026-08-18 已临时关闭
`auto_ban_enabled`，检测器继续运行；关闭时存在 172 条尚未执行的自动封禁动作。

本次把临时措施固化为产品行为：风险检测只形成待人工审核的账号，任何封禁都必须由
owner、admin 或 operator 在运营管理面板点击“确认封禁”后执行。一次点击就是批准，
不增加提交人与审批人分离的双人流程。

同时，operator 在运营管理页面拥有与 owner/admin 相同的业务操作权限；系统管理、用户
管理和其他页面的权限不因此扩大。

## 2. 目标与非目标

### 2.1 目标

- 保持 60 秒风险检测和证据更新，不再由检测器修改 Sub2API 账号或 API Key 状态。
- 所有风险账号统一进入“高风险待审批”状态。
- owner、admin 和 operator 可人工确认封禁、解除封禁、标记误报、撤销例外和修改风控设置。
- operator 可执行运营管理页面内的其他写操作。
- 保留操作人、原因、时间、证据、源状态快照和执行结果等审计信息。
- 安全处理历史待执行自动封禁动作，确保部署和重启都不会恢复执行。

### 2.2 非目标

- 不实现双人复核、审批流转或批量封禁。
- 不改变风险邮箱规则、共享 IP 阈值、七天窗口和付费保护规则。
- 不把仅被标记为高风险的账号排除出运营统计；仍只排除确认封禁成功的账号。
- 不扩大 operator 在运营管理页面之外的权限。

## 3. 核心决策

### 3.1 只允许人工封禁

检测器继续计算原有风险结论，但持久化状态最多为 `high_risk`，不再生成或恢复
`auto_ban` 动作，也不调用 Sub2API 封禁写入。

后端不再接受启用自动封禁的设置请求。风控设置只保留检测器启停等非封禁控制；前端
删除可编辑的“自动封禁”开关，改为固定展示“人工审批”。这是防止误开启的双重保护，
不能只依赖数据库当前值。

### 3.2 人工确认即批准

账号列表和详情中的“确认封禁”调用现有人工封禁入口。请求必须包含非空处置原因。
服务端在执行前重新读取账号和 API Key 当前状态，沿用现有事务、冲突保护和审计记录；
成功后才将风险状态改为 `banned` 并排除运营统计。

付费历史仍是检测阶段的保护信号，但不阻止获授权运营人员基于人工复核结果确认封禁。

### 3.3 历史动作收口

新增风险数据库迁移，为 action 状态增加 `cancelled`，并将所有 `pending` 或 `failed` 的
`auto_ban` 动作更新为 `cancelled`，写入明确的自动封禁停用原因。相关 `ban_pending`
账号改回 `high_risk`，保留账号证据、动作快照和历史事件。

迁移必须幂等。运行时即使遇到迁移前遗留记录，也不得执行自动封禁；恢复函数应停止
参与调度，形成独立于数据迁移的防线。

## 4. 权限模型

运营写角色统一为 `owner`、`admin`、`operator`。

每个写请求仍必须同时满足：

- 当前角色拥有 `operations-management` 页面权限；
- 当前用户已分配目标站点；
- 风控操作只能用于 AIWeLink；
- 请求满足对应业务校验，例如封禁、解封和误报操作必须填写原因。

该权限适用于运营管理页面现有全部写操作，包括内部账号维护、兑换码、余额调整、换算
比例、待分类记录、风险设置、确认封禁、解封和误报处理。operator 不获得角色管理、
系统配置、API Token 或其他管理页面权限。

后端鉴权是权限边界，前端只负责按同一规则展示控件，不能作为唯一保护。

## 5. 数据流

```text
操作/调用日志 -> 60 秒检测 -> 风险证据与 high_risk 状态
                                  |
                                  v
                        运营管理待审批列表
                                  |
                   owner/admin/operator 确认并填写原因
                                  |
                                  v
                    人工封禁动作 + 源状态事务
                                  |
                    成功后标记 banned 并排除统计
```

检测和人工执行由 Growth advisory lock 串行化。人工动作继续在源库写入前创建 action，
源库写入失败时保留可见失败记录，不提前排除运营统计。

## 6. 页面调整

- 风控状态区保留“检测器”开关，将“自动封禁”改为不可编辑的“人工审批”状态说明。
- 规则说明改为“命中规则后进入待审批，确认封禁后才停用账号并排除统计”。
- `ban_pending` 兼容显示为“高风险待审批”，迁移后正常数据不再产生该状态。
- 历史 `auto_ban` 的 `cancelled` 动作显示为“自动封禁已取消”，不得显示“等待恢复”。
- operator 可看到并使用运营管理内全部写控件，不再显示运营只读提示。
- 危险操作继续使用确认弹窗和必填处置原因，不增加批量按钮。

## 7. 错误与并发处理

- 自动封禁设置请求传入 `true` 时返回 400，并说明系统仅允许人工审批。
- 人工封禁与检测器冲突时沿用 409 busy/conflict 响应，由用户刷新后重试。
- 人工封禁执行前源状态发生变化时保持失败关闭，不覆盖未知的新状态。
- 迁移前遗留自动动作即使未被成功转换，运行时也不得恢复执行。
- operator 未分配 AIWeLink 或目标运营站点时继续返回 403。

## 8. 测试策略

- 领域与服务测试：强风险结论在任何设置下都只得到 `high_risk`，不产生自动候选。
- 协调器测试：启用检测时不调用自动恢复和 `disable_account`；遗留动作不会执行。
- 仓储与迁移测试：`cancelled` 约束、历史动作转换和 `ban_pending` 回退均为幂等。
- 路由测试：operator 可执行所有运营写操作和全部风控动作；viewer/maintainer 仍被拒绝；
  未分配站点的 operator 仍被拒绝。
- 前端测试：operator 显示写控件；自动封禁开关消失；人工审批文案、确认弹窗和必填原因正确。
- 回归测试：owner/admin 行为不变，确认封禁成功后统计排除，解封后恢复统计。

## 9. 发布与验证

1. 先保持线上 `auto_ban_enabled = FALSE`，不得在部署前重启会恢复旧动作的旧版本服务。
2. 部署包含迁移和运行时防线的新版本。
3. 验证自动封禁设置为关闭、历史自动动作已取消、风险账号处于待审批状态。
4. 分别使用 operator 和 admin 验证一条非生产测试账号的确认封禁与解封流程。
5. 检查运营统计只排除确认封禁成功的账号，并确认检测器继续按 60 秒更新证据。
