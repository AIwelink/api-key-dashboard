# 飞书扫码登录设计

日期：2026-08-18
目标分支：`achernar/dev`

## 1. 背景与目标

系统当前使用邮箱密码登录，由后端签发自有 JWT，并以 MongoDB 中的本地用户、角色和页面权限作为授权依据。本次增加飞书扫码授权登录，但不把角色和业务权限迁移到飞书。

目标：

- 登录页提供飞书官方扫码授权入口。
- 已绑定飞书的本地用户可以直接扫码登录。
- 尚未绑定飞书的现有用户，在飞书扫码登录时按飞书组织邮箱自动匹配并绑定。
- 尚未绑定飞书的现有用户使用密码登录后，必须完成一次飞书扫码绑定才能进入业务页面。
- 飞书身份找不到本地用户时，允许自动创建用户并登录，但初始业务权限严格为 0，页面提示联系管理员分配权限。
- 继续复用现有本地 JWT、用户状态、角色、页面权限、在线状态和审计体系。
- 保留邮箱密码作为应急入口。

非目标：

- 不使用现有飞书机器人 Webhook 承载登录。
- 不把飞书组织角色自动映射为本系统角色。
- 不长期保存飞书用户 access token 或 refresh token。
- 不自动授予新飞书用户任何业务页面权限。

## 2. 核心决策

采用后端统一处理飞书 OAuth 授权码流程：前端只负责发起授权、展示扫码状态和接收一次性登录结果；App Secret、授权码交换、飞书用户信息读取、身份绑定和本地 JWT 签发均在后端完成。

飞书只负责认证“这个人是谁”，本系统继续负责授权“这个人可以做什么”。业务接口不得直接信任前端传入的飞书用户信息。

## 3. 用户流程

### 3.1 已绑定用户扫码登录

1. 用户在登录页点击“飞书扫码登录”。
2. 前端请求后端创建一次性飞书授权会话。
3. 桌面端打开居中的飞书官方授权窗口并显示二维码；手机端跳转到飞书授权页。
4. 飞书回调后端，后端校验 `state`、交换授权码并读取用户身份。
5. 后端按飞书身份唯一键找到本地用户，检查用户未被禁用。
6. 后端生成一次性登录票据，前端使用票据换取现有系统 JWT 和用户信息。
7. 前端沿用当前登录后的导航与权限逻辑。

### 3.2 现有用户首次扫码自动绑定

1. 后端未按飞书身份唯一键找到用户。
2. 若飞书返回组织邮箱，则对邮箱做去空格和小写规范化。
3. 后端查找同邮箱且尚未绑定飞书的本地用户。
4. 通过带“尚未绑定”条件的原子更新绑定飞书身份；并发失败时重新读取并确认最终绑定关系。
5. 绑定成功后按该本地用户原有角色和权限登录。

如果同邮箱用户已经绑定另一个飞书身份，则视为冲突，不覆盖、不创建重复用户，并提示联系管理员。

### 3.3 现有用户密码登录后强制绑定

1. 后端验证邮箱和密码。
2. 用户已经绑定飞书时，沿用当前登录流程并签发 JWT。
3. 用户尚未绑定飞书时，不签发业务 JWT，只返回短期绑定凭证和飞书授权地址。
4. 前端立即进入飞书扫码绑定流程，用户不能跳过进入业务页面。
5. 回调后端使用绑定凭证确定目标本地用户。此流程已验证本地账号所有权，因此不要求飞书邮箱与本地邮箱相同。
6. 飞书身份未绑定其他用户时，将其绑定到目标用户并签发一次性登录票据。
7. 飞书身份已经绑定其他用户时拒绝覆盖并提示联系管理员。

### 3.4 新飞书用户自动创建

后端无法按飞书身份或组织邮箱找到本地用户时：

1. 创建本地用户，保存飞书显示名、组织邮箱和稳定身份标识。
2. 设置 `authorization_status=pending`。
3. 可以完成登录并访问身份状态页，但 `allowed_views=[]`。
4. 前端只显示“当前账号尚未分配系统权限，请联系管理员调整权限”。
5. 管理员在用户管理页选择角色并确认授权后，将用户改为 `authorization_status=active`，权限立即按角色配置生效。

飞书未返回邮箱时仍可创建待授权用户。系统为数据模型生成不可用于密码登录的内部占位邮箱，不能展示为已验证的用户邮箱，也不能用于后续自动匹配。占位邮箱使用随机用户 ID 生成，不包含原始 `open_id`、`union_id` 或手机号。

## 4. 身份匹配与冲突规则

匹配优先级固定为：

1. 飞书稳定身份唯一键。
2. 飞书组织邮箱与本地规范化邮箱精确匹配，且本地用户尚未绑定飞书。
3. 自动创建待授权用户。

飞书身份唯一键由 `tenant_key` 和优先可用的 `union_id` 组成；当飞书未返回 `union_id` 时使用应用范围内的 `open_id`。数据库同时保存原始身份字段并保存规范化的 `identity_key`，所有查询和唯一约束使用 `identity_key`。

以下情况必须失败，不能自动修复：

- 一个飞书身份试图绑定第二个本地用户。
- 一个已绑定本地用户试图绑定不同飞书身份。
- 同邮箱本地用户已绑定不同飞书身份。
- 回调租户不在允许的飞书租户范围内。
- 本地用户状态为 `disabled`。

## 5. 数据模型

`users` 增加：

```text
authorization_status: "active" | "pending"
feishu_identity:
  identity_key: string
  tenant_key: string
  union_id: string | null
  open_id: string
  user_id: string | null
  name: string | null
  email: string | null
  avatar_url: string | null
  bound_at: datetime
  bound_via: "feishu_email" | "password_binding" | "auto_provision"
last_feishu_login_at: datetime | null
```

兼容规则：历史用户缺少 `authorization_status` 时按 `active` 解释，启动迁移可幂等补写 `active`，不能使现有用户失去权限。

新增索引：

- `users.feishu_identity.identity_key`：仅对字符串值建立部分唯一索引。
- `feishu_auth_sessions.expires_at`：TTL 索引。
- `feishu_auth_sessions.state_hash`：唯一索引。
- `feishu_auth_sessions.ticket_hash`：稀疏唯一索引。

不改变现有用户 `_id`，避免影响工作计划、在线状态、审计和其他以本地用户 ID 关联的数据。

## 6. 授权边界

必须把“已认证”与“已授权”分开：

- `get_authenticated_user`：验证 JWT 和本地用户状态，允许 `pending` 用户访问 `/auth/me`、退出登录和必要的授权状态接口。
- `get_current_user`：在认证基础上要求 `authorization_status=active`，作为所有业务接口的默认依赖。
- `permissions_for_user`：对 `pending` 用户始终返回 `allowed_views=[]`、`default_view=null`，不得回退到 `viewer`。

API Token 仍按现有逻辑运行，不受飞书用户绑定状态影响。

实现时必须审计所有只依赖当前用户的业务路由，确保待授权用户不能绕过页面权限访问数据。前端隐藏菜单只用于体验，不作为安全控制。

## 7. 后端接口

接口契约：

```text
POST /api/auth/feishu/sessions
GET  /api/auth/feishu/callback
GET  /api/auth/feishu/sessions/{session_id}
POST /api/auth/feishu/exchange
POST /api/auth/login
GET  /api/auth/me
```

`POST /auth/feishu/sessions` 创建 `purpose=login` 的授权会话并返回授权 URL、会话 ID 和过期时间。密码登录发现用户未绑定时，由后端创建 `purpose=bind` 且关联目标用户的授权会话。

`GET /auth/feishu/callback` 只处理飞书回调，不直接在 URL 中返回 JWT。成功后保存短期、单次使用的登录票据；桌面弹窗通过受限来源的 `postMessage` 通知父窗口后关闭，无法打开弹窗时回退为同页跳转。

`POST /auth/feishu/exchange` 原子消费登录票据并返回现有 `LoginResponse`。同一票据第二次使用必须失败。

授权会话存储哈希后的 `state` 和票据，不存储可直接使用的明文凭证。授权码交换得到的飞书 access token 仅在当前请求内读取用户信息，随后丢弃。

## 8. 前端体验

登录页：

- “飞书扫码登录”为主按钮。
- 邮箱密码登录保留在次级折叠区域，作为应急入口。
- 发起授权、等待扫码、授权成功、用户取消、二维码过期、网络失败均有明确状态。
- 二维码过期或失败时提供“重新扫码”。

首次绑定：

- 密码验证成功但未绑定时，页面自动进入扫码绑定状态。
- 明确说明本次扫码用于绑定当前系统账号。
- 绑定完成后自动进入原默认页面，无需再次输入密码。

待授权页面：

- 不渲染业务页面和导航入口。
- 显示飞书头像、名称以及“尚未分配权限，请联系管理员”。
- 提供刷新权限和退出登录操作。
- 管理员完成授权后，用户点击刷新即可进入默认页面。

用户管理页：

- 待授权用户置顶，显示“飞书用户 · 待分配权限”。
- 显示飞书绑定状态、最后飞书登录时间和本地用户状态。
- 管理员选择角色并确认后激活权限；管理 owner 仍遵守现有 owner 限制。
- 不显示 App Secret、授权码、飞书 access token 或完整身份唯一键。

## 9. 安全与可靠性

- 生产环境必须配置企业自建飞书应用、固定回调地址和允许租户；不能复用机器人 Webhook。
- App ID、App Secret 只通过后端环境变量读取。
- `state` 使用密码学随机值，有效期 5 分钟且只能使用一次。
- 登录票据有效期不超过 60 秒且只能使用一次。
- 回调跳转目标使用服务端固定白名单，不接受任意前端 URL。
- 弹窗消息校验 `event.origin` 和授权会话 ID。
- 日志中对 `code`、`state`、票据、access token、`open_id` 和 `union_id` 脱敏。
- 绑定和自动创建使用唯一索引、条件更新和重复键重读，处理并发回调。
- 飞书接口设置连接和读取超时；外部失败不能产生半绑定用户。
- 禁用用户在飞书回调成功后仍拒绝签发本地 JWT。

审计动作至少包括：

```text
auth.feishu.login_succeeded
auth.feishu.login_failed
auth.feishu.user_bound
auth.feishu.user_auto_created
auth.feishu.binding_conflict
auth.feishu.ticket_replayed
auth.password.binding_required
user.authorization_activated
```

审计只记录本地用户 ID、结果码和脱敏上下文。

## 10. 配置与上线

新增环境变量：

```text
FEISHU_AUTH_ENABLED=false
FEISHU_APP_ID=
FEISHU_APP_SECRET=
FEISHU_REDIRECT_URI=
FEISHU_ALLOWED_TENANT_KEYS=
FEISHU_AUTHORIZE_BASE_URL=https://accounts.feishu.cn
FEISHU_OPEN_API_BASE_URL=https://open.feishu.cn
FEISHU_REQUEST_TIMEOUT_SECONDS=8
```

上线顺序：

1. 在飞书开放平台创建企业自建应用，配置网页登录回调和读取用户基本信息、组织邮箱所需权限。
2. 部署包含数据兼容、索引和后端接口的版本，保持 `FEISHU_AUTH_ENABLED=false`。
3. 配置生产 App ID、App Secret、回调地址和允许租户。
4. 部署前端扫码入口并开启飞书认证。
5. 使用普通成员、管理员、待授权新用户和禁用用户分别验收。

配置不完整时，后端不得生成不可用授权地址；登录页保留密码入口并显示“飞书登录暂不可用”。

## 11. 测试范围

后端单元和服务测试：

- 授权 URL、`state` 生成与过期。
- 回调成功、取消、缺少参数、飞书接口超时和错误响应。
- 已绑定身份登录。
- 按规范化邮箱绑定现有未绑定用户。
- 密码登录后的指定用户绑定，允许邮箱不同。
- 无匹配用户自动创建 `pending` 用户。
- 无邮箱用户创建内部占位邮箱。
- 同一身份并发绑定和自动创建只产生一个结果。
- 绑定冲突、禁用用户、错误租户、回调重放和票据重放。
- `pending` 用户的 `/auth/me` 可访问，所有业务依赖返回 `403`。
- 管理员分配角色后变为 `active` 并获得对应页面权限。
- 历史用户缺少 `authorization_status` 时权限不变。

前端测试：

- 飞书主入口和密码应急入口。
- 弹窗成功、弹窗被阻止后的同页降级、取消和过期重试。
- 密码用户未绑定时自动进入扫码绑定。
- 待授权页面无业务菜单且可刷新权限。
- 用户管理页待授权用户置顶和授权操作。
- 不在 URL、页面错误或日志中泄露 JWT 和飞书敏感信息。

端到端测试使用可控的飞书客户端替身，不依赖真实飞书服务。生产发布前再执行一次真实企业应用的扫码验收。

## 12. 验收标准

- 桌面端可以通过飞书官方二维码完成登录，手机端可以完成飞书授权。
- 已绑定用户扫码后进入原有角色默认页面。
- 现有未绑定用户首次扫码可按组织邮箱自动绑定并保留原角色。
- 现有未绑定用户密码登录后必须扫码绑定，不能绕过。
- 新飞书用户可以登录，但在管理员授权前无法读取或修改任何业务数据。
- 管理员授权后无需重新创建用户，刷新即可获得相应权限。
- 禁用用户、错误租户、身份冲突、过期和重放请求均被拒绝。
- 飞书 App Secret、授权码、access token 和本地 JWT 不出现在 URL、日志或审计详情中。
- 邮箱密码应急入口仍可用，现有 API Token 行为不变。
