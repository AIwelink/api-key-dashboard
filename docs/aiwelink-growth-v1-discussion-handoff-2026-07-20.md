# AIWeLink 增长数据看板 V1 讨论交接稿

> 日期：2026-07-20  
> 状态：讨论稿，仅用于继续方案设计；不是最终技术规格，也未进入代码实现。  
> 主域名：`aiwelink.cc`  
> API 服务域名：`api.aiwelink.cc`

## 1. 背景

`api.aiwelink.cc` 当前运行开源 Sub2API，负责用户注册、登录、API 调用、充值等核心业务。团队计划在 `aiwelink.cc` 建设品牌主页，并新增推广来源追踪能力。

由于 Sub2API 会长期跟随开源上游更新，不希望为了增长追踪、主页或登录流程长期维护一个大幅修改的 Fork。增长能力应尽量放在 Sub2API 之外。

## 2. V1 核心目标

为每个具体推广来源生成唯一链接，并持续观察该链接带来的用户是否完成：

```text
点击链接
→ 注册
→ 首次成功调用
→ 第一次充值
→ 第二次充值
→ 再次成功调用
```

最终需要回答：

> 哪个具体平台、帖子、群或推荐人带来了用户，这些用户后来是否注册、调用、充值、二次充值并继续使用。

## 3. 已确认的业务范围

### 3.1 追踪对象

追踪访问客户站点、注册并使用 API 的终端用户，不追踪当前管理后台的内部员工操作。

### 3.2 归因颗粒度

采用“渠道 + 具体推广来源”颗粒度，不能只统计到平台级别。

每条帖子、每个群、每位推荐人都应生成不同链接，例如：

- 小红书某一条帖子；
- V2EX 某一条帖子；
- Linux 论坛某一条帖子；
- Telegram 某一个群；
- 微信某一个群；
- 某一位熟人推荐；
- 其他论坛或渠道的具体入口。

后台还要记录推广负责人和链接生成时间。

### 3.3 个人邀请能力

V1 以渠道和具体推广活动为主，数据结构需要预留未来按推广员或现有用户生成个人邀请链接的能力。

### 3.4 归因 Cookie

接受使用 30 天有效期的第一方匿名归因 Cookie。

注册前系统只能识别匿名浏览器访问，不能确认真实用户身份。注册成功后才将 Sub2API 用户 ID 与推广链接绑定。

限制：跨设备、无痕模式或清除 Cookie 后可能被识别为不同匿名访客。V1 不使用浏览器指纹。

### 3.5 唯一归属

一个正式账号只能归入一条推广链接，避免在多条推广来源中重复计算。

同一匿名浏览器在注册前先后访问多个推广链接时，最终采用第一条还是最后一条仍未确认，见“待确认问题”。

## 4. 已确认的指标口径

### 4.1 点击人数

按推广链接下去重后的匿名访客数计算，不等同于原始 HTTP 请求次数。

### 4.2 注册账号数

只有 Sub2API 注册成功才算注册，只有点击不算注册。

### 4.3 成功调用账号数

至少有一次成功获得模型响应的账号数。失败请求不计入。

### 4.4 完成充值账号数

至少有一笔独立且成功到账充值的账号数。

### 4.5 二次充值账号数

至少有两笔独立且成功到账充值的账号数。单笔订单的状态重复更新不能算二次充值。

### 4.6 继续调用账号数

首次成功调用后又发生至少一次成功调用的账号数。

当前 V1 按“第二次成功调用”理解，不要求必须跨天。若后续希望衡量真正留存，可另加 D1、D7、D30 成功调用留存。

### 4.7 金额

按推广链接汇总成功充值金额和退款金额。退款必须按真实退款事实统计，不能只根据订单取消状态推断。

### 4.8 排除规则

团队内部账号和测试账号不进入正式统计。具体识别方式尚未确认，可考虑显式名单、用户标签或账号分组。

## 5. 推广外链格式

### 5.1 已确认格式

公共推广链接统一使用：

```text
https://aiwelink.cc/r/{code}
```

示例：

```text
https://aiwelink.cc/r/7km4q2xd
```

`/r/*` 由服务端或边缘服务直接处理，不进入 React/Vue 主页渲染。

### 5.2 链接码建议，尚待最终确认

- 8 位随机小写字符；
- 排除容易混淆的 `0`、`o`、`1`、`i`、`l`；
- 链接码生成后永久不变；
- 停用后的链接码不能重新分配；
- 平台、帖子、群和负责人等可读信息保存在后台，不编码进 URL。

### 5.3 个人邀请命名空间建议

未来可预留：

```text
https://aiwelink.cc/i/{code}
```

这只是当前建议，尚未最终确认。

## 6. `/r/*` 请求链路

推荐链路：

```text
浏览器请求 aiwelink.cc/r/{code}
→ 跳转服务校验链接
→ 记录点击事件和匿名访客
→ 设置 30 天归因 Cookie
→ 返回 HTTP 302
→ 用户进入品牌主页或 api.aiwelink.cc 注册页
```

关键规则：

- 使用服务端 `302`，不依赖 JavaScript；
- 不使用容易被浏览器长期缓存的 `301`；
- 即使用户关闭 JavaScript，仍能完成记录和跳转；
- 链接不存在、停用或过期时，不应继续归因；
- 默认跳转品牌主页、直接跳注册页，还是允许每条链接配置目标，尚未确认。

建议的域名路由：

```text
aiwelink.cc/          → 品牌主页前端
aiwelink.cc/r/*       → 增长跳转服务
api.aiwelink.cc/*     → 原版 Sub2API
```

同一个域名不代表由同一个前端应用处理。Nginx、CDN 或边缘函数可以在加载主页前端之前截获 `/r/*`。

## 7. Sub2API 与增长系统的边界

### 7.1 推荐方向

不修改 Sub2API 源码，不在其核心表中增加推广归因字段。

原因：

- Sub2API 是持续更新的开源上游；
- 修改注册、认证、数据库和前端核心流程会增加长期合并冲突；
- 自定义分支仍可跟随上游更新，但每次都需要重放补丁并解决冲突；
- 增长追踪不是 Sub2API 的核心职责。

### 7.2 推荐的独立代码库

建议建立一个独立于 Sub2API 的自有仓库，例如：

```text
aiwelink-growth
├─ redirect-service   # 处理 GET /r/{code}
├─ admin-api          # 创建、停用链接和查询统计
├─ sync-worker        # 只读同步 Sub2API 的用户、调用和支付事实
├─ migrations         # 增长数据库结构
└─ tests
```

这是一个仓库中的多个模块或进程，不需要为每个模块建立独立仓库。

主页是否也放入这个仓库形成小型 monorepo，尚未确认。

### 7.3 推荐部署边界

- `aiwelink-growth` 独立部署和独立发布；
- Sub2API 继续使用官方上游版本或尽可能接近上游版本；
- 增长系统通过稳定适配层只读 Sub2API 数据；
- Sub2API 升级时验证适配器，不合并增长功能到上游代码。

## 8. 数据库边界草案

### 8.1 Sub2API 数据库仍是业务事实源

继续负责：

- 用户账号和注册时间；
- 登录和 Session；
- API 成功调用记录；
- 充值订单；
- 退款记录；
- 用户余额和业务状态。

增长系统不得复制密码、Session、API Key 或其他认证密钥。

### 8.2 增长数据库负责

建议保存：

- 推广平台；
- 具体来源类型，例如帖子、群、推荐人；
- 具体来源名称和原始地址；
- 推广负责人；
- 推广链接与随机码；
- 链接状态和生成时间；
- 匿名访客；
- 点击事件；
- Sub2API 用户 ID 与推广链接的唯一归属；
- 内部账号和测试账号排除规则；
- 为看板准备的行为事实或汇总快照。

### 8.3 上游数据适配

当前项目已具备连接客户站点数据库和扫描远程表结构的基础。后续需要核实 Sub2API 实际版本中的：

- 用户表及注册时间字段；
- 成功调用日志及成功状态判断；
- 充值订单和到账状态；
- 第二笔独立订单的判定；
- 退款事实来源；
- 用户 ID 在上述表中的关联方式。

不能仅凭表名猜测指标，必须以实际字段、索引和状态机为准。

## 9. 注册归因与 Session 讨论

### 9.1 Session 原则

不建议在 `aiwelink.cc` 与 `api.aiwelink.cc` 之间复制 Session。

Sub2API 应继续作为认证和 Session 的唯一拥有者。若主页直接调用 API 注册或登录接口，浏览器可以保存 `api.aiwelink.cc` 返回的 Host-only、`Secure`、`HttpOnly` Session Cookie，随后跳转到 API 站时自动携带。

跨来源请求需要精确 CORS 白名单、`Access-Control-Allow-Credentials: true` 和 CSRF/Origin 校验，不能使用 `Access-Control-Allow-Origin: *`。

当前仍需确认 Sub2API 实际使用的是服务端 Session Cookie，还是存放在 `localStorage` 的 Token。

### 9.2 不修改 Sub2API 时如何绑定注册

目前推荐在 `api.aiwelink.cc` 前增加外置增长网关，只处理或观察注册成功链路：

```text
归因 Cookie
→ 注册请求
→ 原版 Sub2API 注册成功
→ 外置网关获得 Sub2API 用户 ID
→ 增长数据库写入用户与推广链接的唯一绑定
```

普通请求、登录响应和 Session Cookie 原样透传给 Sub2API。

这一方案仍需确认以下部署事实：

- 是否能控制 `api.aiwelink.cc` 前面的 Nginx、Traefik、Cloudflare 或其他反向代理；
- 注册成功响应是否包含稳定用户 ID；
- 如果不包含，是否能通过官方当前用户接口或只读数据库安全获取；
- 网关如何避免记录注册密码等敏感请求内容。

## 10. Sub2API 自定义首页和 iframe

Sub2API 支持把自定义首页配置为 Markdown、HTML 或外部 URL。

当配置内容是以 `http://` 或 `https://` 开头的网址时，Sub2API 不会跳转，而是在自己的首页中通过 iframe 嵌入该网址。地址栏仍然停留在 `api.aiwelink.cc`。

iframe 仅解决页面展示，不解决 Session 同步或增长归因。

### 10.1 已验证的 `aiwelink.cn` 拒绝连接原因

本次讨论中曾把另一个服务页面 `https://aiwelink.cn/` 填入 iframe。2026-07-20 实测该站响应包含：

```http
X-Frame-Options: SAMEORIGIN
```

因此浏览器禁止它被 `api.aiwelink.cc` 嵌入，并显示“拒绝连接”。`.cn` 是本次 iframe 测试域名，不是当前增长方案的主域名。

如果未来要嵌入自有 `aiwelink.cc` 页面，应移除冲突的 `X-Frame-Options`，并使用精确 CSP 白名单，例如：

```http
Content-Security-Policy: frame-ancestors https://api.aiwelink.cc
```

iframe 内的注册和登录按钮还需要进行顶层跳转，避免把 Sub2API 页面继续加载在 iframe 中。

是否最终使用 iframe 尚未确认。独立品牌主页仍应以 `https://aiwelink.cc` 顶层页面为主。

## 11. 看板 V1 展示要求

每条推广链接直接展示：

- 点击人数；
- 注册账号数；
- 完成过成功调用的账号数；
- 完成过充值的账号数；
- 完成过二次充值的账号数；
- 首次调用后仍继续调用的账号数；
- 充值金额；
- 退款金额。

点击每个数字可以查看对应账号名单。

单个账号详情需要展示：

- 归属的推广链接、平台和具体来源；
- 注册状态和注册时间；
- 首次成功调用时间；
- 首次充值时间和金额；
- 二次充值时间和金额；
- 最近成功调用时间；
- 是否发生退款及退款金额；
- 按时间排序的行为时间线。

## 12. V1 验收链路

创建一条“某篇小红书帖子”的推广链接，用非内部测试账号执行：

```text
点击链接
→ 注册
→ 成功调用
→ 第一次充值
→ 第二次充值
→ 再次成功调用
```

验收时必须满足：

1. 账号唯一归属于该小红书帖子对应链接；
2. 注册、调用、充值、二次充值和继续调用均显示已完成；
3. 点击各项指标可以在名单中找到该账号；
4. 账号详情中的来源、金额和行为时间线与实际记录一致；
5. 内部或测试账号不污染正式指标；
6. 整个链路不要求修改 Sub2API 核心源码。

## 13. 待确认问题

下一轮讨论建议按以下顺序继续：

1. `/r/{code}` 默认跳品牌主页、直接跳注册页，还是允许每条链接配置目标；
2. 同一匿名浏览器点击多条推广链接后注册，采用第一条还是最后一条；
3. `code` 是否最终固定为 8 位无歧义小写随机字符；
4. 是否正式预留 `/i/{code}` 个人邀请命名空间；
5. 品牌主页与 `aiwelink-growth` 是否放在同一仓库；
6. `aiwelink.cc` 和 `api.aiwelink.cc` 当前实际部署方式及反向代理控制权；
7. Sub2API 当前登录态究竟是 Session Cookie 还是前端 Token；
8. Sub2API 注册成功响应能否稳定取得用户 ID；
9. Sub2API 用户、成功调用、充值和退款的实际表结构与状态字段；
10. 内部账号和测试账号通过名单、标签还是账号分组排除；
11. 看板允许的数据延迟，例如实时、1 分钟或 5 分钟；
12. 是否最终使用 Sub2API iframe 自定义首页。

## 14. 给后续讨论的约束

- 当前阶段只做设计，不直接写业务代码；
- 不把增长功能写入 Sub2API 上游核心代码；
- 不复制用户密码、Session、API Key 或其他密钥到增长数据库；
- 所有付费、退款和调用指标必须来自可核验的业务事实；
- 先确认实际部署、认证方式和数据库字段，再确定接口与表结构；
- 任何账号在正式统计中只能归属一条推广链接。
