# 账号探测与运营分析系统设计

## 1. 背景

需要增加一个整体的账号信息收集和运营系统，为后续 Agent 系统提供足够稳定、可追溯的数据。目标不是只看当前账号池状态，而是能回答这些运营问题：

- 账号从加入 sub2 到封号，通常能正常使用多久。
- 最近封号是否变多，是否说明风控收紧。
- 哪些时间段更容易封号。
- 哪些账号类型、购买来源、上传人、分组更容易出问题。
- 账号使用了多少额度后更容易异常。
- 当前账号池按最近死亡速度还能撑多久，什么时候需要补号。
- 结合账号成本后，分析整体运营成本和账号质量。

基础探测要求：

- 每 3 分钟探测 sub2 里的账号状态。
- 如果发现新账号加入 sub2，需要开始计时，即使这个账号不是从本系统推送过去的。
- 如果账号异常，并且异常信息包含 401，需要记录为疑似封号事件，记录状态和时间，计算账号正常使用时间。
- 账号可能 401 后恢复正常，之后又再次 401，所以不能只记录一次最终状态，需要保存状态变化时间线。
- 如果两个 sub2 账号邮箱相同，应视为错误添加。系统需要在错误警告里提示，同时账号运营记录按同一个邮箱身份归一。

## 2. 现有系统已有数据

当前系统已经有一些基础数据，可以复用：

- `sub2api_accounts_cache`
  - 保存 sub2 当前账号快照。
  - 已包含 `site_id`、`sub2api_account_id`、`group_ids`、`status`、`schedulable`、`error_message`、`email`、`plan_type`、`last_used_at`、5h/7d 用量等。
- `sub2api_dashboard_trends`
  - 保存站点和分组维度的用量趋势。
- `accounts`
  - 保存本地账号 JSON 和 metadata。
  - metadata 里有上传人、账号类型、购买来源、池状态、sub2 绑定信息等。
- `account_operations`
  - 保存本地操作日志。
- `account_problems`
  - 保存问题账号记录。

## 3. 当前缺口

现有数据更偏“当前状态”和“人工操作”，不足以做长期运营分析。主要缺少：

- sub2 账号状态变化历史。
- 账号生命周期 summary。
- 每次进入 sub2 的使用周期记录。
- 401 封号事件序列。
- 401 后恢复、恢复后再次封禁的多段事件模型。
- sub2 手动删除账号的识别。
- sub2 删除后重新加入同邮箱账号的连续累计。
- 直接在 sub2 加入、但本地库里没有的账号身份记录。
- 每个分组是否开启详细探测的配置。
- 原始探测日志的保留、聚合、清理策略。

## 4. 核心设计逻辑

### 4.1 身份归一

账号运营身份不能只按 `remote_account_id` 判断。

原因：

- sub2 账号被手动删除后重新添加，`remote_account_id` 可能变化。
- `name` 只是方便查看的命名，可能重复，不能作为身份。
- 邮箱才是账号的稳定身份。

设计：

- 账号长期身份使用 `site_id + normalized_email`。
- `remote_account_id` 表示这个账号在 sub2 中的一次实例。
- 同一个邮箱被删除后重新加入，开启新的 session，但累计用量、封号次数、生命周期分析仍归到同一个 identity。
- 如果同一站点同一时刻出现多个相同邮箱 remote account，写入重复邮箱告警事件。

### 4.2 Session 概念

一个邮箱账号可能多次进入 sub2：

- 第一次加入 sub2，生成一个 session。
- 被手动删除或从 sub2 消失，session 结束。
- 后续同邮箱重新加入 sub2，开启新的 session。

每个 session 记录这一次在 sub2 里的运行周期，identity 记录长期累计。

### 4.3 状态事件时间线

只保存当前状态不够，需要保存状态变化事件。

长期保存的事件包括：

- 新发现账号。
- 状态变化，例如 `active -> abnormal`。
- error_message 变化。
- `schedulable` 变化。
- 分组变化。
- 发现 401。
- 401 后恢复正常。
- 账号从 sub2 消失。
- 连续缺失后确认删除。
- 删除后同邮箱重新出现。
- 重复邮箱告警。

普通每 3 分钟探测样本只短期保留，聚合后删除。

### 4.4 sub2 手动删除判断

不能因为一次探测没有看到账号，就立刻认为账号被删除。

判断逻辑：

- 只有在本次账号列表完整拉取成功后，才允许判断缺失。
- 连续 2 到 3 次完整探测都缺失，才标记 `remote_removed_confirmed`。
- 第一次缺失先记录 `missing_suspected`，不结束 session。
- 确认删除后，结束当前 session，保存删除时间和最后状态。
- 如果后续同邮箱再次出现，记录 `remote_reappeared`，开启新 session。

### 4.5 用量累计

删除后重新加入，同邮箱账号的使用用量需要累计。

设计原则：

- identity 层保存长期累计用量。
- session 层保存本次进入 sub2 的用量。
- event 层保存关键节点的用量快照。
- sample 层短期保存每次探测轻量用量。

如果 sub2 有累计总消耗字段：

- 优先直接使用累计字段。
- 每次探测保存当前累计值。

如果只有 5h/7d 窗口用量：

- 只能通过 delta 估算长期累计。
- 当窗口用量增加时，累加差值。
- 当窗口用量下降，可能是窗口刷新或账号重置，不能按负值扣减。
- 需要记录 `usage_reset_detected` 标记，避免误算。

### 4.6 分组级开关

不是所有分组都需要详细记录。比如 free 池没有必要保存大量细节。

设计：

- 每个 `site_id + group_id` 可以配置是否开启详细记录。
- 关闭详细记录时，只更新当前缓存，不保存完整探测样本。
- 即使关闭详细记录，也建议保留非常关键的异常统计，例如重复邮箱、401 计数、账号数量变化。
- plus/team/k12/pro 或核心使用池建议开启详细记录。

### 4.7 存储控制

每 3 分钟探测一次，如果每次都长期保存完整快照，数据会增长很快。

设计：

- 原始探测样本短期保存，建议 7 到 14 天 TTL。
- 状态变化事件长期保存。
- 每小时/每天聚合一次运营指标。
- 聚合完成后，旧的原始样本自动删除。
- Agent 优先读取 summary 和 stats，不直接扫原始样本。

## 5. 数据模型设计

### 5.1 `group_observability_settings`

每个 sub2 分组的探测和记录配置。

主键：

- `_id`: `{site_id}:{group_id}`

字段：

- `site_id`: sub2 站点 ID。
- `group_id`: sub2 分组 ID。
- `group_name`: 分组名称快照。
- `enabled`: 是否启用探测。
- `detailed_enabled`: 是否启用详细时间线和短期样本。
- `probe_interval_seconds`: 探测间隔，默认 180。
- `sample_retention_days`: 原始探测样本保留天数，默认 7 或 14。
- `event_retention_days`: 事件保留天数，默认长期或 365。
- `aggregate_retention_days`: 聚合统计保留天数，默认长期或 730。
- `record_usage_samples`: 是否记录用量样本。
- `record_status_events`: 是否记录状态事件。
- `record_duplicate_email_warning`: 是否记录重复邮箱告警。
- `status`: `active` / `disabled`。
- `created_at`
- `updated_at`
- `updated_by`

建议默认：

- free 分组：`detailed_enabled=false`。
- plus/team/k12/pro 使用池：`detailed_enabled=true`。
- 备用池可开启事件记录，但可以关闭高频样本。

## 6. 探测流程

### 6.1 每 3 分钟轻量探测

流程：

1. 读取 active 的 sub2 site。
2. 读取该站点 group 配置。
3. 拉取 sub2 账号列表。
4. 标记本次拉取是否完整成功。
5. 对每个账号做标准化：
   - remote id
   - email
   - status
   - schedulable
   - error_message
   - group_ids
   - plan_type
   - usage snapshot
6. 按 `site_id + normalized_email` 找 identity。
7. 新邮箱创建 identity。
8. 新 remote id 创建 session。
9. 和上一状态比较，发现变化则写 event。
10. 检测 401。
11. 检测重复邮箱。
12. 对本次没看到、但上次存在的账号，执行缺失计数。
13. 连续缺失达到阈值后，确认删除并关闭 session。
14. 写 probe run summary。

### 6.2 401 判断

判断来源：

- `status` 为异常类状态。
- `error_message` 包含 401。
- `error_message` 包含：
  - `token invalidated`
  - `token revoked`
  - `authentication failed`
  - `invalid_request_error`
  - `token_invalidated`

事件分类：

- `token_invalidated`
- `token_revoked`
- `authentication_failed`
- `unknown_401`

### 6.3 恢复判断

如果上一个关键状态为 401，后续账号出现以下情况：

- `status` 回到 `active`。
- `error_message` 清空。
- 测试通过。
- `schedulable=true`。

则写入 `401_recovered` 事件，并更新 identity/session 的 recovery 计数。

### 6.4 重复邮箱判断

同一个 `site_id + normalized_email` 在同一次完整探测里出现多个不同 `remote_account_id`：

- 写 `duplicate_email_detected`。
- identity 里更新 `duplicate_remote_count`。
- 前端错误警告里提示。
- 运营统计上按一个账号 identity 计算，但 session 可保留多个 remote instance 以便排查。

## 7. 聚合与清理

### 7.1 小时聚合

每小时运行一次：

- 读取最近一小时 events 和 samples。
- 计算小时统计。
- 写入 `account_ops_hourly_stats`。
- 标记已聚合的 probe run。

### 7.2 天级聚合

每天运行一次：

- 汇总小时统计。
- 计算风险趋势。
- 生成 `account_ops_daily_stats`。

### 7.3 原始样本清理

使用 TTL：

- `remote_account_probe_samples.expires_at`
- 默认保留 7 到 14 天。
- detailed 关闭的分组不写样本，或只保留 1 天。

长期保留：

- identity。
- session。
- status events。
- hourly/daily stats。

## 8. Agent 可读取的信息

Agent 主要读取：

- `remote_account_identities`
- `remote_account_sessions`
- `remote_account_status_events`
- `account_ops_hourly_stats`
- `account_ops_daily_stats`
- 账号池容量数据
- 通知配置

Agent 应能回答：

- 最近 24 小时 401 是否异常增加。
- 最近账号平均存活时间是否下降。
- 哪个分组最近风险最高。
- 哪个购买来源质量下降。
- 哪个上传人的账号近期异常率高。
- 哪个时间段容易封号。
- 使用到多少额度后更容易封。
- 当前补号是否应该提前。
- 建议补号数量。
- 是否需要通知钉钉/TG。

## 9. 前端页面建议

新增运营分析页面，或放在账号池管理/系统管理下：

- 分组探测配置：
  - 开关详细记录。
  - 保留天数。
  - 探测间隔。
- 账号生命周期查询：
  - 按邮箱查询。
  - 查看 session。
  - 查看 401/恢复/删除事件线。
- 风险概览：
  - 最近 1h/6h/24h/7d 401 数。
  - 401 率。
  - 平均存活时间。
  - 风险分组排行。
- 重复邮箱告警：
  - 同邮箱多个 remote id。
  - 所属分组。
  - 当前状态。
- Agent 建议：
  - 是否需要补号。
  - 建议补号数量。
  - 风险原因。

## 10. 和现有系统的关系

现有 `sub2api_accounts_cache` 继续作为当前状态缓存。

新增系统不替代它，而是补充：

- `sub2api_accounts_cache`: 当前状态。
- `remote_account_identities`: 长期账号身份。
- `remote_account_sessions`: 每次进入 sub2 的周期。
- `remote_account_status_events`: 状态变化时间线。
- `remote_account_probe_samples`: 短期探测样本。
- `account_ops_hourly_stats` / `account_ops_daily_stats`: 长期运营指标。

现有 30 分钟容量刷新不建议承担 3 分钟探测任务。

建议新增独立轻量探测 scheduler：

- 3 分钟只拉账号列表和轻量字段。
- 30 分钟继续做 dashboard、usage、容量统计。
- 状态变化时可触发一次额外 usage 快照，但不要每 3 分钟对所有账号拉重用量接口。

## 11. 默认策略建议

- 探测间隔：180 秒。
- 删除确认：连续 3 次完整探测缺失。
- 样本保留：核心分组 14 天，普通分组 7 天，free 可关闭。
- 事件保留：长期。
- 小时统计保留：长期或 730 天。
- 天级统计保留：长期。
- 401 风险判断默认窗口：
  - 最近 1 小时。
  - 最近 6 小时。
  - 最近 24 小时。
  - 最近 7 天。

## 12. 第一阶段实现范围

第一阶段建议只实现基础闭环：

1. 分组探测配置表。
2. 每 3 分钟轻量探测。
3. identity/session/event 三张核心表。
4. 401 检测和恢复检测。
5. sub2 删除/重加检测。
6. 重复邮箱检测。
7. 原始样本 TTL。
8. 简单小时聚合。

第二阶段再做：

- 风险评分。
- Agent 分析接口。
- 通知机器人联动。
- 账号成本分析。
- 前端完整运营分析页面。
