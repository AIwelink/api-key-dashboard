# 菜单与页面设计

> **文档状态：页面职责历史汇总。** 当前菜单顺序、中文名称、英文路径、移动端默认页和角色可见性以 `frontend/src/App.tsx` 为准；新增页面不要只修改本文。

本文档按当前开发优先级重新设计后台菜单。现阶段以手动流程为主：先把账号上传、查看、编辑、分池、验证、手动加入/退回等基础工作流跑通，再逐步开发自动化推送和 Agent 分析。

## 1. 上传账号

页面定位：

前期最主要工作区。团队制作的新账号、renew 后账号、购买账号、历史账号、已知问题账号，都先从这里进入系统。

当前/近期功能：

- 填入模式：手动填写字段并粘贴单个或多个账号 JSON。
- 解析模式：批量导入 JSON 后逐个补充缺失字段。
- 支持松散 JSON，例如 `{...} {...}` 中间没有逗号。
- 支持上传意图 `upload_intent`：
  - `new`：新制作账号。
  - `renew`：更新/续用旧账号 JSON。
  - `purchase`：购买账号。
  - `historical`：历史账号。
  - `known_error`：已知问题账号。
- 导入后默认进入账号总库，`pool_status = library`。
- 用户填写的管理字段同时写入：
  - `metadata`，用于本系统查找和决策。
  - `account_json.extra`，用于保持导出到 sub2api 时携带信息。
- 上传人、修改人自动绑定当前登录用户。
- 重复账号导入时尝试更新已有账号。
- 如果已有账号处于实际使用中，后端阻止覆盖。

后续增强：

- 批次详情页。
- 导入错误定位。
- 批次标记：新账号、旧账号、问题账号、renew。
- 批量导入后快速进入“可用池”或“验证流程”的入口。

主要接口：

```text
POST /api/import-batches
POST /api/imports/preview
```

## 2. 待办

页面定位：

从账号池管理中拆出独立页面，用来展示系统给团队的处理建议。

现阶段策略：

先做介绍页，不做复杂功能。

未来功能：

- 展示账号需求：
  - 哪个池缺多少账号。
  - 为什么缺账号。
  - 是 5h 容量不足、7d 容量不足，还是 active 数量不足。
- 展示问题账号：
  - 哪些账号从使用池退回。
  - 错误原因。
  - 出错时间。
  - 使用金额、剩余容量、最后请求时间。
- 展示处理建议：
  - 制作新账号。
  - renew 旧账号。
  - 更新 JSON 后重新验证。
  - 弃用。
- 后续再考虑分配处理人。

主要接口：

```text
GET /api/todo-items
```

## 3. 账号列表

页面定位：

账号总库页面。主要负责筛选、查看和编辑各种账号，不承担太多池化操作。

当前/近期功能：

- 查看本地所有账号。
- 搜索邮箱、上传人、修改人、备注、人工状态标注。
- 按账号类型、支付类型、手机绑定、状态标注筛选。
- 按本地状态筛选：
  - `library`：总库。
  - `available` 或后续定义状态：准备进入可用池。
  - `reserve`：使用备选池。
  - `active`：实际使用中。
  - `problem`：问题账号。
  - `discarded`：弃用。
- 编辑账号：
  - 管理字段。
  - `account_json`。
  - 备注。
  - 人工状态标注。
- 删除或软删除账号。
- 导出 sub2api JSON。

需要补强：

- 更完整的编辑功能。
- 编辑时保留账号生命周期状态，不因普通编辑改变池状态。
- 查看账号详情和历史操作记录。
- 从账号列表跳转到所属池、批次、待办。

主要接口：

```text
GET    /api/accounts
GET    /api/accounts/{account_id}
PATCH  /api/accounts/{account_id}
DELETE /api/accounts/{account_id}
GET    /api/exports/sub2api
```

## 4. 可用池

页面定位：

展示“看起来可用、但还没有进入使用备选池”的账号。这里主要是准备区。

账号来源：

- 新创建账号。
- renew 后账号。
- 历史账号经过人工整理后准备复查。
- 没有直接标注错误的账号。
- 人工判断可以进入备选流程的账号。

当前设计状态：

待开发。可以先基于 `metadata.pool_status = library` 加筛选实现初版，但后续建议独立页面。

近期功能设计：

- 查看准备进入备选流程的账号。
- 按上传意图筛选：
  - `new`
  - `renew`
  - `purchase`
  - `historical`
  - `known_error`
- 按账号类型、支付类型、是否绑定手机、上传批次筛选。
- 手动标记：
  - 加入使用备选池。
  - 标记问题。
  - 弃用。
  - 需要验证。
- 批量操作入口。

注意：

可用池不是 sub2api group，只是本地筛选和处理状态。

## 5. 使用备选池

页面定位：

展示已经通过验证或人工确认、可以根据逻辑推送到 sub2api 的账号。它是实际使用池的候补区。

账号来源：

- 验证通过的账号。
- 人工确认可用的账号。
- 从可用池手动加入的账号。
- renew 后重新确认可用的账号。

当前设计状态：

待开发。现在账号列表里已有“加入备用池”的轻量入口，后续要拆到这个页面。

近期功能设计：

- 查看备选账号。
- 按目标账号池、账号类型、优先级、风险标记筛选。
- 手动操作：
  - 退回可用池。
  - 直接加入实际使用池。
  - 推送到 sub2api。
  - 标记问题。
  - 弃用。
- 展示每个账号的：
  - 优先级。
  - 验证状态。
  - 最近验证时间。
  - 历史错误。
  - 支付类型。
  - 是否绑定手机。
- 后续自动化推送会从这里选择账号。

注意：

第一版仍以手动操作为主。自动推送前必须先实现锁、失败回滚、远端不确定状态处理。

## 6. API 账号池状态

页面定位：

展示 sub2api 远端状态，并作为测试环境下的远端 sub2api 控制台。这个页面可以执行明确的远端测试/删除/回退操作，但所有写操作必须保存本地快照、动作记录和审计日志。

当前功能：

- 查看 sub2api 站点状态。
- 测试 sub2api 连接。
- 手动刷新数据库缓存。
- 查看远端 groups。
- 查看 group 下账号。
- 单账号远端测试。
- 单账号从 sub2api 手动删除并退回本地可用池。
- 单账号从 sub2api 手动删除并退回本地总库。
- 展示远端账号状态：
  - active。
  - error。
  - disabled。
  - paused。
- 展示账号调度信息：
  - schedulable。
  - 并发。
  - priority。
  - 错误信息。
  - 最近使用时间。
  - 过期时间。
  - 5h/7d 用量窗口。

边界：

- 这个页面读取 MongoDB 中的 sub2api 缓存。
- 手动刷新会访问远端 sub2api。
- 远端测试只记录测试结果，不改变本地生命周期。
- 手动删除/退回会先把远端账号快照写入本地库，再删除 sub2api 账号，并修改本地生命周期。
- 批量远端删除暂不开放，后续必须先做预览和二次确认。
- 专用账号验证分组只用于测试，不作为实际使用池或容量补位目标。

主要接口：

```text
GET   /api/sub2api-sites
PATCH /api/sub2api-sites/{site_id}
POST  /api/sub2api-sites/{site_id}/test
POST  /api/sub2api-sites/{site_id}/refresh
GET   /api/sub2api-sites/{site_id}/groups
GET   /api/sub2api-sites/{site_id}/groups/{group_id}/accounts
POST  /api/sub2api-sites/{site_id}/accounts/{account_id}/test
POST  /api/sub2api-sites/{site_id}/accounts/{account_id}/manual-delete
POST  /api/accounts/{account_id}/verify-via-sub2api
```

## 7. 账号池逻辑管理

页面定位：

账号池逻辑管理页当前先作为“目标分组选择”和“后续自动化入口”。sub2api 分组只用于选择后续推送目标；当前备选账号池仍然来自本地可用池手动加入的 `pool_status = reserve` 账号。

`API 账号池状态` 和 `账号池逻辑管理` 必须读取同一份 sub2api 账号池缓存，后台只保留一条同步链路：

```text
sub2api -> refresh_site_cache -> sub2api_groups_cache / sub2api_accounts_cache / sub2api_cache_meta -> 前端页面按需读取
```

任意页面触发 `POST /api/sub2api-sites/{site_id}/refresh` 后，都视为同一份账号池数据已更新，前端需要让相关页面缓存失效并重新读取 MongoDB 缓存。不要为账号池逻辑管理再创建独立的分组同步集合、接口或后台任务。

现阶段策略：

暂时不深度开发，以手动流程和 sub2api 分组为主。

- 去掉整体待办展示。
- 去掉页面内容量检查入口。
- 去掉页面内创建本地池配置入口。
- sub2api 分组来自统一账号池缓存，只作为后续推送目标分组。
- 当前备选账号池来源：本地 `accounts.metadata.pool_status = reserve`，也就是从可用池手动加入的账号。
- 本地池配置 `api_pools` 仅作为历史配置/后续开发预留展示，不参与当前判断和推送。
- “可用池”和“使用备选池”的手动流转目标分组读取统一 sub2api 分组缓存，写入账号 `metadata.sub2api_group_id` / `metadata.sub2api_group_name`，不再依赖本地池配置。

已有/近期功能：

- 选择 sub2api 站点。
- 同步 sub2api 账号池数据，统一写入 `sub2api_groups_cache`、`sub2api_accounts_cache` 和 `sub2api_cache_meta`。
- 展示分组列表：账号数、活跃账号、限流账号、状态。
- 选择一个 sub2api 分组作为后续推送目标。
- 展示本地 reserve 备选账号整体参数，不展示账号明细。
- 账号明细和手动操作继续放在“使用备选池”页面。
- 展示本地池配置，但标注为暂不实际使用。

后续功能：

- 重新设计本地池配置与 sub2api 分组的映射关系。
- 自动从使用备选池挑选账号。
- 自动推送到 sub2api。
- 推送失败回滚。
- 实际使用账号异常退回。
- 容量不足告警。
- 根据风险权重做推荐排序。

主要接口：

```text
GET   /api/sub2api-sites
POST  /api/sub2api-sites/{site_id}/refresh
GET   /api/sub2api-sites/{site_id}/groups
GET   /api/sub2api-sites/{site_id}/groups/{group_id}/accounts
GET   /api/api-pools  # 仅展示历史/预留配置
```

## 8. Agent分析

页面定位：

后续智能分析入口。用于辅助判断系统当前应该制作新账号、renew 旧账号、处理问题账号，还是调整池策略。

现阶段策略：

先做介绍页，不接真实 Agent 决策。

未来功能：

- 汇总账号池状态。
- 汇总待办。
- 分析问题账号类型。
- 分析支付类型、绑卡、手机号、历史错误和使用情况。
- 给出建议：
  - 新制作多少账号。
  - renew 哪些旧账号。
  - 哪些账号建议弃用。
  - 哪些池优先补充。
- Agent 只做辅助判断，最终执行仍走系统规则和人工确认。

注意：

Agent 不能绕过本地安全逻辑。即使 Agent 出错，前面的本地状态机、容量检查和手动操作仍要可靠。

## 10. 日志

页面定位：

统一查看系统运行日志和操作记录，辅助开发阶段排错和后续运维。

当前状态：

后端已经有整体日志系统：

- `logs/app.log`
- `logs/access.log`
- `logs/error.log`

已有审计页面可查看数据库中的操作审计。

后续页面设计：

- 日志页面可以整合：
  - 系统运行日志摘要。
  - 请求错误。
  - 慢请求。
  - sub2api 刷新错误。
  - 账号导入错误。
  - 操作审计。
- 支持按时间、模块、request_id、错误级别筛选。
- 日志页面不展示敏感 token、完整 `account_json` 和密码。

## 当前阶段开发重点

近期优先级：

1. 上传账号：继续作为主要工作区打磨。
2. 账号列表：补强编辑功能和账号详情。
3. 可用池：从账号总库里抽出准备处理的账号。
4. 使用备选池：承接验证通过或人工确认的账号。
5. 待办和 Agent分析：先做介绍页。
6. 账号池逻辑管理：读取统一 sub2api 账号池缓存选择目标分组；本地池配置只展示为后续预留。

当前阶段不优先做：

- 全自动推送 sub2api。
- Agent 自动执行。
- 复杂审批流。
- 多处理人分派。
